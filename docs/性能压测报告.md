# 性能压测报告

- 日期：2026-11-08
- 环境：本机 Windows，后端 `127.0.0.1:8081`，MySQL 8 / Redis（Docker），语音走本地管线，文本走 DeepSeek 上游 API
- 工具：`backend/scripts/load_test.py`
- 身份：压测脚本默认使用同一个演示账号（shared token），因此并发请求共享同一用户的限流与用量记录

## 三、10 并发（10 个独立账号）

为避免单账号限流影响，另注册 10 个独立账号，每个虚拟用户使用自己的 token 重跑：

| 阶段 | p50 | p95 | max |
|---|---:|---:|---:|
| 创建会话 | 4152.2 ms | 7315.7 ms | 8234.9 ms |
| 响应头 | 247.8 ms | 2309.1 ms | 2484.8 ms |
| 首个流式事件 | 5526.3 ms | 7697.6 ms | 8621.7 ms |
| 首个 Token | 9312.8 ms | 11261.5 ms | 12259.3 ms |
| 完整回复 | 9649.5 ms | 11533.3 ms | 12529.9 ms |

成功率 10 / 10，总耗时 16.6 s，吞吐 0.60 响应/秒。

结论：**换成独立账号后延迟仍然高**，说明瓶颈不在单用户限流或用量行，而在
「创建会话时的开场生成 + 上游大模型并发吞吐」。本机单实例同时打 10 路生成时，
上游首 Token 被拉长到 9–13 s。

## 四、发现并修复的问题

首次单账号 10 并发时出现 1 个 500，日志定位为：

```
IntegrityError: (1062, "Duplicate entry 'demo-student-2026-11-08' for key 'model_usage_daily.PRIMARY'")
```

原因：同一用户的并发请求同时执行「先查再插」的用量累加，触发主键冲突。

修复：插入冲突时回滚并改为原子 `UPDATE calls = calls + 1`（`app/infrastructure/rate_limit.py`），
新增并发回归测试 `tests/test_model_quota.py::test_concurrent_usage_recording_is_atomic`。
修复后重跑 10 并发：**10/10 成功，0 失败**。

## 五、结论与建议

1. 功能正确性：修复后并发成功率 100%，无降级回复，10 个独立账号同样 100%。
2. 延迟瓶颈在上游大模型并发吞吐：单用户首 Token 约 3.1 s，10 并发（含独立账号）放大到 9–13 s。
3. 创建会话在 10 并发下 p50 4–5 s（单用户 19.6 ms），与账号是否独立无关；
   下一步应对 `POST /training-sessions` 做火焰图，重点看开场生成的模型调用与连接池等待。
4. 建议：演示/答辩环境以成功率与降级率为准；若要在 10 并发下守住 3 s 首字，
   需要预热开场白缓存、限制生成并发或换更高吞吐的模型端点。
