# 性能压测报告

- 日期：2026-11-08
- 环境：本机 Windows，后端 `127.0.0.1:8081`，MySQL 8 / Redis（Docker），语音走本地管线，文本走 DeepSeek 上游 API
- 工具：`backend/scripts/load_test.py`
- 身份：压测脚本默认使用同一个演示账号（shared token），因此并发请求共享同一用户的限流与用量记录

## 二、10 并发（同一演示账号）

- 发布门禁：`firstTokenP95 ≤ 3000 ms` **未通过**（实际 12.9 s）

## 三、发现并修复的问题

首次 10 并发时出现 1 个 500，日志定位为：

```
IntegrityError: (1062, "Duplicate entry 'demo-student-2026-11-08' for key 'model_usage_daily.PRIMARY'")
```

原因：同一用户的并发请求同时执行「先查再插」的用量累加，触发主键冲突。

修复：插入冲突时回滚并改为原子 `UPDATE calls = calls + 1`（`app/infrastructure/rate_limit.py`），
新增并发回归测试 `tests/test_model_quota.py::test_concurrent_usage_recording_is_atomic`。
修复后重跑 10 并发：**10/10 成功，0 失败**。

## 四、结论与建议

1. 功能正确性：修复后并发成功率 100%，无降级回复。
2. 延迟瓶颈在上游大模型：单用户首 Token 已约 3.1 s，10 并发时放大到 10–13 s；
   这是共享同一账号 + 本机网络到上游的实测值，不代表多账号生产环境。
3. 创建会话在 10 并发下 p50 涨到 5.2 s（单用户 19.6 ms），说明高并发下开场生成/数据库写入存在竞争，
   建议后续用多账号 token 文件复测，并对创建会话做火焰图定位。
4. 建议把「发布门禁」改为按账号数区分：本机单实例演示环境以成功率与降级率为准，首 Token 目标另设。

## 五、复现

```powershell
$env:LOAD_TEST_PASSWORD="Student123!"
backend\.venv\Scripts\python.exe backend\scripts\load_test.py `
  --base-url http://127.0.0.1:8081/api/v1 `
  --email student@example.com --users 10 `
  --output reports/load-test.json
```

报告为机器可读 JSON；`--tokens-file` 可让每个虚拟用户使用独立 token，更接近生产。
